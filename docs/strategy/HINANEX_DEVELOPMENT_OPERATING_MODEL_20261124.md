## 役割と作業権限

| 役割 | 担当する判断・作業 |
| --- | --- |
| Owner | 製品方針、学内MVP・公開の範囲、重要な変更と作業権限を決裁する。既存規約が指定する受入は指定された人間が行う。 |
| 司令塔（ChatGPT） | 作業パッケージ、仕様・契約、依存関係と受入基準を管理する。Codexからの証拠を審査し、技術的GO/HOLDと統合順を示す。 |
| Codex | 指示された範囲で調査、詳細設計、実装、テスト、独立監査、PRの作成・更新を行う。結果、対象SHA、残件を司令塔へ返す。 |
| 人間の共同Merge Captain | @1kz-ma1 / @kouta1029 が現行規約に基づき最終統合判断を記録し、GitHub上で正式統合する。代理実行が許される場合も対象ごとに明示指示が必要。 |

作業パッケージは原則1件ずつ進める。開始時に権限ID、対象、許可・禁止、依存と受入基準を記録する。L-PRIV、L-FLOW、L-CONTRACT、L-QA、L-DEVICEは作業分類に使用する。Codexの内部調査は並行可能。A–Eはリポジトリ上の責務・Scope Guardとして引き続き適用する。

今回の権限は `WP001_DEVELOPMENT_OPERATING_MODEL_AND_ASSET_INVENTORY_AUTHORIZED_SCOPED`。対象は読取棚卸し、運用文書と報告、文書限定Draft PR。製品コード、既存機能PRの更新・マージ・Close、保護・Render設定、手動デプロイは範囲外。

## 実装から統合まで

1. **司令塔が作業を発行する。** Owner決裁が必要な境界を確認し、ベース、依存、対象ファイル、テスト、データと配信の範囲を指定する。
2. **Codexが実装と実装側の検証を行う。** ソースHEADとベース、実行環境、テスト入力、PASS / FAIL / NOT_RUNの内訳、未解決事項をDraft PRへ記録する。
3. **独立監査を行う。** 対象HEADまたは原本・ハッシュを固定して実装側の自己報告と区別できる証拠を取る。監査主体、対象、実施内容、観測した結果、残件を記録する。独立再現ができない場合は理由を記録する。実装者と別の検証が必要な場合は司令塔が担当を指定する。
4. **司令塔が成果を受け入れ、技術的GO/HOLDを示す。** 受入は対象と証拠単位で明示する。HEAD変更時は変更範囲を照合し、影響のある監査・CIを再確認する。
5. **人間の共同Merge Captainが正式統合する。** 最新main、確定HEADの必須 `test`、適用中の保護、スコープ、契約、データ安全、非公開、依存と実機QA分類を確かめ、規約の監査ログを残す。前提PRを先に扱い、Squash後のstackはmainとの差分を再確認する。
6. **統合後の状態を確認する。** mainのSHAとCI、必要な場合はRenderの配信SHA・実配布物、既定の公開境界を記録する。開発完了、コード統合、実機QA、原本受入、公開許可、実配信は別状態で管理する。

取り違えを防ぐため、PRと実機台帳には対象SHAと証拠URLを添える。実機QAは [現行の運用仕様](HINANEX_IMPLEMENTATION_FIRST_DEVICE_QA_20261113.md) と [#372](https://github.com/1kz-ma1/HINANEX/issues/372) に従う。繰越はDQA-IDと未実施内容を記録する。UNKNOWN/null、公式の原値と出典、合成と公式データの分離、配布ガード、権利・安全・公開の各人間承認を維持する。
