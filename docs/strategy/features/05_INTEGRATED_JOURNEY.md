# F05 将来の統合体験：災害情報→避難施設→本人選択→参考経路

- 状態: **FUTURE DESIGN**。2026-10-30時点の既存比較・施設選択UIは**この完成UXの前提条件ではない**。
- 設計原則: F01（災害情報）、F02（避難施設）、F03（事前準備）、F04（時系列シミュレーション）は**どれも単独で価値がある**。F05は全てを直列に強制する機能でなく、必要に応じて利用者が移動できる統合導線。
- 2027-02-09の洪水デモ目標は維持しつつ、未受入の経路・現在の開設・安全性を事実として示さない。

## 統合の候補ジャーニー

1. ユーザーがF01で公式ハザード・想定条件・地域を確認（又はF02から直接開始）。
2. 本人が必要と判断した場合にF02の参考施設へ進む。**地域/ハザードの文脈だけを引き継ぎ、元ソースと状態を上書きしない**。
3. 利用者が施設の出典、指定災害、未確認事項を確認し、2件等を比較する（UI形式は今後のUX検証で決める）。
4. 本人が候補を選び、必要なら公式の避難情報や参考経路の外部表示へ進む。**本人が選んだ=アプリが安全な行き先と認定した**ではない。
5. F03に任意保存した自治体レベルの地域設定があれば、初期表示候補の補助に使う。現在地/正式な緊急避難先と見なさない。F04は災害進行の教育的・想定条件付き再生で、実際の警報と混同しない。

## 接続点は最小化（概念設計、実際のAPI/RegionExportは未変更）

- region context: 公式/ユーザー指定の自治体コード、元となる地図スコープ、本人が選んだこと。未取得/不一致時は明示。
- hazard context: `hazard_type`、公式の想定・ソースID・対象時点や版（もし独立検証済み）。`risk_score`や`is_safe`のような根拠のない断定を渡さない。
- facility reference: **元ソースに紐づく固定ID**と出典、検証済み属性/未確認、本人の選択状態を区別。別ソースの施設名類似でIDを自動統合しない。
- optional local prep: 端末内任意の地域設定のみ。UIから明示許可を得て利用し、位置・家族・健康・連絡先等は初期設計に含めない。
- navigation: 出発点/到着点・公開可能な検証済み位置・外部サービス利用条件/同意を別に扱う。経路の表示=通行安全性ではない。

## インテグレーションゲート

1. F01単体で原本/想定条件/出典/失敗時が説明できる。
2. F02単体で公的施設の元属性とUNKNOWNを保持して検索/詳細が使える。
3. F03が未実装・設定保存拒否でもF01/F02は使用可能。F04が非対応地域でも基礎体験が利用可能。
4. シナリオ、地域、施設を切り替えたら以前の選択/画面結果を誤流用しない。
5. API/JSON共有契約が必要ならD/共有設計PRを先に審査し、既存Schema v0.9・enum・null意味を壊さず Add→Migrate→Remove。
6. 実機操作と、原本受入/位置・公開承認は別判定。ルート表示は安全な避難経路保証ではない。根拠が足りない連携はHOLD。

## 今実装しないこと

- 既存GIS比較UIへ全機能を直結して完成形へ固定する。
- ログイン/投稿/サーバーDB前提の機能、未確認の災害時自動避難推薦。
- F04の公式洪水仮定とF01の静的ハザードを一致するものと仮定した合成、未検証位置をルート終点にする。

## 次の設計レビューで決めること

- 利用者が**何から始められるか**（災害地図直行／施設探し直行／準備から開始）。
- どの画面で何を説明し、災害時に何操作で必要な情報へ到達できるか。
- 再利用できる最小の「地域・災害文脈」の契約。実際のシナリオ/データを混ぜない。
- 2027-02-09デモでは参考経路をどの範囲で表示し、何を未実装と明言するか。
