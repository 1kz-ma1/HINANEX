## 仕様書を起点に開発する流れ

1. 対象機能を1つ選択し、仕様書の **目的 / 独立動作 / 現状 / 対象外** を読む。
2. 現行main、root `AGENTS.md`、対象領域の `AGENTS.md`、README、既存Contract・テストを確認。仕様と矛盾すれば**推測で修正せず人間へ報告**。
3. 1画面・1操作・1データ状態を単位に作業Issue/小PRを切り出す。依存先とPR baseを明記する。
4. 成功・欠損/UNKNOWN・失敗/範囲外の3系統でテスト。実ブラウザ・公式原本の受入はCIと別に記録。
5. 実装結果に合わせ、**提案仕様との差をPRへ記録してから**必要最小限で仕様改訂する。実装していない未来の記述を「完成」へ昇格させない。

## 明確な区分

- `CURRENT`: mainに存在する、コード/仕様で確認できる範囲。mainにあるだけで本番デプロイ済みや実災害時の利用許可を意味しない。
- `PROTOTYPE`: Draft PR、合成データ、固定シナリオ、隔離試作など。実利用向けの安全性/品質受入は別。
- `FUTURE`: 技術調査・要件候補。APIの利用許諾や実装可能性は未確定。
- `HOLD`: 根拠、原本版、同一性、位置、個人情報、契約、承認など不足し、後段利用へ進めない状態。
