- **作成/最終見直し: 2026-10-30**
- **Status: PROPOSED / DESIGN-ONLY**。オーナーの運用判断待ち。優先順位表は実装許可・人間C承認・公開許可ではない。
- **対象:** このディレクトリのF01〜F19の候補と、今後の新規アイデア。仕様本文は個別ファイル、本書は「何をいつ検討・着手するか」の**唯一の優先度表**。
- **最重要:** 施設検索・ハザード情報・準備・時系列シミュレーションは**独立して成立させる**。F05で後から必要な部分だけ接続する。既存の2件比較UIを完成UXと決めつけない。
- **目標:** 2027-02-09の学内MVP（1地域×洪水の説明可能な閲覧→参考施設の条件/根拠確認→本人選択→可能なら参考経路のデモ）。**未受入データ・位置・公式意味・経路は達成のために推測しない**。経路ゲート未成立なら未実装として発表する。

## 1. 優先順位と作業状態は別々

**優先度**（本書専用。既存Dの `Capability/Discovery` や `score` と一切無関係）:

| 優先 | 意味 | 何をするか |
| --- | --- | --- |
| **P0 / MVP** | 2/9の小さな洪水体験に不可欠な利用者価値・誤認防止・基礎アクセシビリティ | 最小スライスを選んで作業。全機能のフル実装を意味しない |
| **P1 / Next** | P0と並行で**限定調査/独立試作**する価値が高いがMVPの統合を妨げない | 調査のみ、または独立した小Prototype。先に調べる=先に公開するではない |
| **P2 / Later** | 基礎UX・出典/運用が整ってから段階拡張する機能 | 仕様は保持、実装枠は予約しない |
| **P3 / Conditional** | 認証・ライブデータ/運用体制・権利・高リスク安全審査などを要する機能 | 専用の承認条件成立まで保留。静的サイトで無理に代替しない |
| **ICEBOX** | 発想は記録するが、効果/出典/責任/安全のいずれかが説明できず採否未定 | 優先を与えず、必要な根拠を確認してから昇格 |

**進捗**（別軸）：`IDEA` / `SPEC_DRAFT` / `RESEARCH` / `PROTOTYPE` / `READY_FOR_SLICE` / `IN_PROGRESS` / `REVIEW` / `PARTIALLY_MERGED` / `DONE_IN_SCOPE` / `HOLD` / `DROPPED`。これらは**計画用の文字列**で、既存アプリのenumではない。PRが存在してもその機能全体がDONEとは限らず、`DONE_IN_SCOPE`は受入れたスライスとSHA/テストを明記した場合のみ使う。

## 3. 3名で同時並行する作業の上限

- **オーナー**：学校にいる間だけHINANEXの**P0の中核スライスを最大1件**選んで実装・レビュー。他の時間はAP学習に集中。中断が必要なリスク/重大な不具合以外のアイデアは本書の「新規アイデア控え」にメモしておく。
- **信頼できる班員**：**F03の独立Prototypeを最大1件**担当予定。PR #311の存在を確認し、重複実装しない。既存GISと接続/本番へ統合する判断はオーナーが後日実施。
- **新メンバー（班員Sと混同しない）**：**F04の公式API調査を最大1件**担当予定。Issue #341の収集は完了。実データ・APIの大量呼出し・本番コードを作る権限は委任されていない。
- **1人1アクティブの原則**。調査やレビューで詰まったら状況を報告して`HOLD`にし、無関係な別機能を勝手に開始しない。担当名は固定職掌ではなく当面の作業予定。
- PRの存在・CI PASSだけで統合・リリース承認にはしない。Review/mergeはroot `AGENTS.md`とMerge Captainに従う。

## 4. 新規アイデアの受け入れ方（スコープ拡大防止）

1. 思い浮かんだアイデアは**最初は`ICEBOX`の1行**（利用者の問題、期待する体験、依存しそうな公的ソース/安全リスク、提案者/日付）に書く。**実装・Issue/PR作成はしない**。
2. 学校での定期的な見直しで、既存F01〜F19の拡張か新しい機能かを判定。重複なら既存仕様へ追記候補とし、むやみにIDを増やさない。
3. 利用者にとっての効果、独立スライスの小ささ、公的ソース/ライセンスの実現性、既存資産の再利用、3人での作業負荷をそれぞれ **高/中/低/未確認** で説明する。**安全やプライバシーの未解決を点数で相殺しない**。
4. P0の既存作業と交換する場合は**何を遅らせるか**を明記し、オーナーが採用した場合に限り本表の優先度を改訂する。『良さそう』だけではactiveに入れない。
5. READY_FOR_SLICEになる条件: (a) 1利用者行動が具体的 (b) 現在の公開/根拠で表示可能 (c) 失敗/UNKNOWNを定義 (d) 依存PR/契約が判明 (e) テスト・受入1件とownerがいる (f) 他のアクティブ作業と競合しない。
6. 実装開始時にのみ担当Issue/PRを作成・紐付ける。スライスが検収されたら、ここに状態・SHA/受入・次に必要な情報を記録する。**巨大な一括PRにしない**。

## 5. スライス単位の可視化（例）

| スライス | 今の順位 | 次にできること | 完了条件 | 開始判断 |
| --- | --- | --- | --- | --- |
| H01 / F01洪水独立閲覧 | **P0** | 施設選択なしで原本・凡例・対象範囲を確認 | PC/スマホ、成功/欠損/障害の3ケース、参考と明示 | オーナーの次の中核実装候補 |
| S01 / F02施設単独閲覧 | **P0** | 一覧・詳細でソース/UNKNOWN/位置未確認を表示 | 座標無しも見られ、危険/安全を推定しない | H01と並列に増やさず、別スライスとして選ぶ |
| P01 / F03準備UI | P1 | 明示保存/再表示/削除の隔離UI | 端末内・失効・保存拒否テスト/任意操作 | 信頼できる班員の担当候補 |
| T00 / F04公式API調査 | P1 | 公式URL、版、利用/再配信、CORS/制限、データ形を報告 | 実確認/未確認/未実行を区別した調査書 | 新メンバーの担当候補 |
| J01 / F05最小接続 | **P0目標・後段** | 独立H01/S01を渡された地域文脈だけで接続 | 未承認施設/経路が自動推薦されない | H01/S01各自の受入が前提 |
| R00 / F07参考経路可否 | **P0ゲート判断** | 必要な位置・規約・同意の要件確認 | 経路表示可能/不可を根拠付きで明記 | データ未承認なら保留し代替デモを検討 |

**順番の意味:** P0が複数でも同時にすべて着手しない。まずH01（独立洪水）、次にS01（独立施設）、最後にJ01（必要な小接続）を推奨。F07は公開/参照の安全ゲートが通るまで利用者への経路案内にしない。

## 7. 実装・承認との分離

- 共通の災害データ状態は [DATA_STATES_AND_GATES](DATA_STATES_AND_GATES.md) / D Contract/Cレビューが正本。本書のP0・状態名は事業優先度であり、情報の信頼度・ソース承認・避難適合性とは無関係。
- 本書が「P0」としても、同じソース/版/災害に対するA原本・D処理・C人間検証・GIS公開審査・運営の表示範囲審査を省けない。
- `FUTURE`資料、Draft PR、CI成功、利用者自身のチェック、他ソースの距離・名称一致から、施設の正式指定位置/入口/災害時開設・安全/経路を自動承認しない。
- 本書を更新しただけで班員への依頼を開始したことにはならない。本人に引き継ぐときはIssueと該当F仕様をセットにする。
