## 1. 背景と目標

PRごとの人間による実機確認がkouta・オーナー・班員Sの待機原因になっている。学校・試験・その他の予定と両立するため、**実装と自動回帰を平時の主作業とし、物理端末特有の検証を事前に決めた日へまとめる**。検証を省略するのではなく、待機を減らし、結果・担当・端末・修正履歴を残す。

**実装先行の原則は「mainへ素早く入れる」ことと同義ではない。** 最新main、required `test`、Contract互換、データ/プライバシー/公開の禁止条件を守れないPRは従来どおりBLOCK。例外は決裁と別途Issueが必要。

## 2. 開発から実機受入までの標準ステート

| 状態 | 内容 | 次に進む条件 |
| --- | --- | --- |
| `IMPLEMENTED` | 実装・仕様/テストを更新した | 対象の自動テストとレビュー |
| `AUTOMATED_VERIFIED` | CI・必要な実Chrome、契約/静的bundle検査が成功 | 最新base/依存/スコープをMerge Captainが確認 |
| `INTEGRATED_MAIN` | mainへ統合、デプロイは別判定 | QA必要ならIssue #372へ登録し後続作業を続ける |
| `DEVICE_QA_DEFERRED` | 実機項目と検証回・端末・責任者（未定可）を記録した | 予定回の実機検証 |
| `DEVICE_QA_PASSED` | 人間の端末実測のPASS証跡を記録した | 機能別受入判断 |
| `RELEASE_APPROVED` | 人間が正式公開対象とリスクを承認した | 公開手続き/配信テスト |
| `PUBLISHED` | 承認済み範囲の配信が確認された | 通常監視・回帰検証 |

複数の軸を別々に記録する。**`INTEGRATED_MAIN`≠`DEVICE_QA_PASSED`≠`RELEASE_APPROVED`≠`PUBLISHED`**。特にF02はmainの検証コード保全と実施設一覧の一般公開を区別し、既存RenderのF02/F03非公開ガードを解除しない。

## 3. PRの実機QA分類（必須）

PR作成時に`.github/pull_request_template.md`の「Device QA disposition」で**1つだけ**選ぶ。

- `NOT_REQUIRED`：docs-only、端末固有差分なし等。理由と代替自動検証を明記
- `DEFERRED`：mainへ非公開・安全に統合可能だが操作感等の実機検証を次回に繰越。**[Issue #372](https://github.com/1kz-ma1/HINANEX/issues/372)のDQA-ID/コメントURLを必ず記載**（後日QAの証跡/端末/版を辿れるようにする）。PRテスト欄には`Not run: physical device`と残す
- `DONE`：確認した人間・端末/OS/ブラウザ・対象commit/ビルド・手順・PASS/FAILを記載。AI/エミュレータの結果を実機に見せない
- `BLOCKING`：破損、重大なアクセシビリティ/実装成立性、個人情報、未承認の災害データ/経路公開等、次回待ち不可。Issueと担当を記載し、必要ならDraft/merge: blocked

**DEFERREDでもmain統合できる条件**：最新main追従、既存必須CI+変更に必要なテスト成功、Contract/データ/公開の安全審査、未承認コードは配布物からの確実な除外、QAリストへの登録、Merge Captainの確認。赤/保留CIを実機QA延期で正当化しない。

## 4. 約2週ごとのQAバッチ（候補日）

時間帯・班員の空き・端末は**未確定**。確定しなければ日付を移し、実装を止めない。詳細と検証対象は[Issue #372](https://github.com/1kz-ma1/HINANEX/issues/372)を正本とする。

| QA枠 | 予定日（JST・暫定） | 主目的 |
| --- | --- | --- |
| QA-1 | 2026-12-06 | F01/F02結合・最小モバイルUX |
| QA-2 | 2026-12-20 | 追加UI・アクセシビリティ・操作回帰 |
| QA-3 | 2027-01-10 | MVP結合フローと異常時フォールバック |
| QA-4 | 2027-01-24 | 発表候補の最終受入・重大不具合再検証 |
| QA-5 | 2027-02-03 | 発表デモの通し・予備手順・説明の整合 |

原則1回**60～90分**。会の1週間前を目途に3～5重要フローを選定し、前日に対象SHA/ビルド/URL/合成入力を固定。検証開始時に実機・OS・ブラウザを記録し、テストは`PASS / FAIL / BLOCKED / NOT_RUN`で区別する。新たなFAILは独立Bug Issueへ。低優先の未完了は次のQA回へ持ち越す。実装中の端末確認が設計の成否を決める場合のみ小さな即時スパイクを例外として認める。

## 6. 役割分担とブロッカーの扱い

- **kouta / 洪水ユーザー体験（高さ）**：F01・F02・F05の小スライスを実装。通常のPCブラウザ自動回帰とA11Yを先に整備し、Safari/スマホ特有の確認だけDQAへ。実機担当を自動的にkoutaへ押しつけない
- **オーナー / 基盤・地域×災害の拡張（横・縦）**：データ/出典・Contract/RegionExport、独立C検証、統合判断。PRごとの端末確認を基本的に要求しない
- **班員S / 出典調査**：公的一次資料/API調査。書類の人間承認と物理端末操作は別工程。検証日まで実装班を待たせない
- **Merge Captain / AI支援**：PRのQA区分、必要なDQA登録、週次のバックログ棚卸し、CI/公開遮断/差分のレビュー、QAセッション手順作成。**人間の実機PASS/一次資料承認をAIが代行したと主張しない**
- 従来の**A–EディレクトリScope Guardは現行のまま**。成果責任（2トラック）と変更権限（A–E）は別。変更案[Draft #282](https://github.com/1kz-ma1/HINANEX/pull/282)が未統合の間、制約を緩和しない。2トラックの仕様化[Draft #361](https://github.com/1kz-ma1/HINANEX/pull/361)と重複する主張を本書で実装済みと扱わない

## 7. 中断・割込み・品質管理の境界

定期QA日を待たずに`BLOCKING`とする候補：データの破損/消失、本人同意なしの外部送信、未承認位置/施設安全性/開設/経路の配信、実機でしか確認できないコア機能成立性、緊急性のある重大セキュリティ・アクセシビリティ障害。Stop Conditionが成立した場合は[AGENTS.md](../../AGENTS.md)が優先し、オーナーに明示する。

公式一次資料やCによるSource-to-Output整合、D Contract/Schema、ライセンス、人間による災害情報・安全性の最終受入は、**デバイスQA日とは独立した必須ゲート**。実機待ちを減らすことは安全ゲートの削除ではない。

## 8. 運用の確認方法・完了条件

1. 各PRにDevice QA区分・自動検証・安全/公開の区分を記録する
2. DEFERREDはDQA-IDと対象SHA・端末・期待操作・検証回を#372に追加する
3. 定期QAの7日前にIssueテンプレートから回ごとのQA Issueを作る（QA対象と受入結果を分離）
4. 結果を元DQAと各機能Issueへ戻し、FAILは再現手順を付けてBug Issueへ
5. 隔週を目安に「QA未登録PR」「長期未確認」「重大未解決」「非公開ガード変化」を棚卸しする（自動実行と称しない）
6. 最終成果について、実装・CI・実機・人間安全受入・公開/発表の各ステータスを独立して報告する

**今回の採用範囲は開発運用のみ**。2/9の機能仕様や対象災害の安全性を承認するものではない。参照：[3軸MVPロードマップ](./HINANEX_THREE_AXIS_ROADMAP_2027-02-09.md)、[関連実機QA Issue #299](https://github.com/1kz-ma1/HINANEX/issues/299)、[F02 Issue #355](https://github.com/1kz-ma1/HINANEX/issues/355)、[F02 Publication Gate #366](https://github.com/1kz-ma1/HINANEX/issues/366)。
