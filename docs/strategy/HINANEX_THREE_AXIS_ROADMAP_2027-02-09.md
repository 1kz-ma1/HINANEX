# HINANEX 3軸成長戦略・2027年2月9日を目標とする利用体験MVP仕様（提案）

- 策定日: 2026-10-19
- 状態: **PROPOSED / FUTURE DESIGN**（本書自体は実装・承認・統合・本番安全性の証明ではない）
- 対象: 最終発表に向けた中期開発方針・受入基準
- 変更範囲: 共有の戦略文書のみ。既存コード、データ、Schema、運用承認を変更しない
- 期限: **2027-02-09**（ユーザーが提示した目標日。達成を確約するものではない）

## 1. 意思決定の要旨

これまでの HINANEX は「地域（横）×災害種別（縦）」に対応できる検証可能なデータ基盤の整備を進めてきた。今後は第3軸として **ユーザーに直接届く価値・利用体験の完成度（高さ）** を加える。

**2027-02-09 までの優先目標:** 対象を限定した洪水シナリオで、正本として確認できる災害情報に応じた施設の条件抽出、出典・判断根拠・未確認事項の比較表示、利用者による避難先の選択、選択先への経路の参考表示を、一連のデモとして実証する。

地域・災害種別の拡大を無条件に先行させない。対象範囲の Source → Export → UI の品質基準を満たしたうえで、まず高さを増やす。地域・災害種別の拡張可能性と、既存の地域×災害の小規模検証戦略は維持し、一般化の再検証を後段で行う。

**最重要の境界:** 施設の候補抽出／比較／経路の表示は、**その施設や経路が災害時に安全・開設中・推奨先であるとの認定ではない**。利用者の選択を「HINANEX が安全性を確定した」と解釈してはならない。

## 2. 3つの成長軸

| 軸 | 意味 | 成長の例 | 当面の扱い |
| --- | --- | --- | --- |
| 横：対応地域 | 独立に原本を検証した地理的範囲 | 既存の3地域の検証 → 他地域で同一フローを再現 | 拡大より対象範囲内の品質を優先 |
| 縦：災害種別 | 出典と災害別の意味を独立検証した種類 | 洪水 → 土砂災害等（別の原本／属性の承認が必要） | 洪水を主軸とする。未検証種別を推測追加しない |
| 高さ：利用者価値 | ユーザーが実際に行える判断・行動の深さ | 出典表示 → 条件抽出 → 根拠付き比較 → 選択 → 経路参考表示 | **2027-02-09 までの重点投資軸** |

3軸の同時最大化を目的にしない。高さを増やす開発で新たな欠損項目・運用上の制約が判明したら、A/D/C の基盤側へフィードバックする。基盤完成の判定は「全地域で完璧」ではなく、**対象スライスで証跡付きの受入条件を満たすこと**により行う。

## 3. 現在地と未実装の境界

### CURRENT / 既存の実装・実証で扱える範囲（ソース／検証記録に基づく）

- A/D/C で、公開データ取得・原本の証跡・形式の正規化・Capability / Gap / RegionExport・独立検証を扱う基盤がある。
- GIS は確認済みの位置・公式洪水向け掲載地点の参考探索・出典／元データの表示を扱い、未確認の施設属性は推測で埋めない。
- 江戸川・新潟・名古屋の形式差や座標欠損、災害別属性の意味不明を明示する検証実績がある。過去の件数は時点付き観測値であり、現在の完全性や洪水安全性の証明ではない。
- 公開向け GSI 洪水デモの案内・ピン選択・元ソース参照等の実装がある（個別の最新実機受入／デプロイ状態とは区別する）。

### CURRENT / 未解決であり先に維持すべきゲート

- [Issue #268](https://github.com/1kz-ma1/HINANEX/issues/268) に記載された最新原本の時点・真正性、人間による変更／同一施設判断、3地域再生成の正式な受入は継続課題。
- [Issue #48](https://github.com/1kz-ma1/HINANEX/issues/48) の新潟市 ODS 記号は未確認の意味を勝手に確定しない。
- [Issues #134](https://github.com/1kz-ma1/HINANEX/issues/134) / [#141](https://github.com/1kz-ma1/HINANEX/issues/141) の異なる原本同士の施設同一性は、独立した人間の確認なしに自動結合しない。
- 災害時の開設状況、混雑、現実の通行可能性、施設・経路の総合的安全性の自動認定は、現段階では **未実装／未受入** として扱う。

### FUTURE / 本提案で新たに目指すもの

- 取得時点と信頼度を明示できる災害情報を条件へ変換し、施設属性と突き合わせて参考候補を抽出する。
- 根拠・該当条件・不明／未確認事項を、利用者が比較しやすい同一画面に表示する。
- 利用者が**自ら選択した**候補について、外部地図サービス連携等を使った**参考経路**を表示する。
- 上記を安全な避難先／安全な経路の自動推薦と誤認させない。

## 4. 目指す体験（1地域×洪水の縦スライス）

1. **状況を指定・取得**: 利用者が対象地域または明示許可した現在地を指定し、確認可能な洪水情報／検証済みシナリオを読み込む。情報源・対象範囲・公表／取得時点・取得失敗を明示する。
2. **対象候補を抽出**: 災害別に意味が確認済みの施設属性だけを照合する。不明は UNKNOWN／UNVERIFIED のまま残し、開設中や安全性を推測しない。
3. **根拠付きで比較**: 候補ごとに施設名・所在地・該当条件・情報時点・出典・制約・不明点を確認できる。単一の独自「安全スコア」に置き換えない。
4. **本人が選択**: 「候補を選ぶ」は利用者操作であり、アプリによる避難適否の承認ではない。自治体の広域避難方針・災害時の公式指示への導線を残す。
5. **経路を参考表示**: 選択地点への地図上の経路を表示する。ルート計算元と更新時点を示し、浸水・通行止め・橋梁・入口・避難先の開設を検証していない経路を**安全経路**とは呼ばない。必要なら外部サービスで開き直せる。

**デモの基本入力は、再現可能な保存済みシナリオでもよい**。現在発生中の災害を扱うライブ自動取得は、出典・更新頻度・障害時動作・最新性に独立した受入証拠がある場合のみ追加する。ライブ連携できないときにサンプルを「現在の災害情報」と表示しない。

## 5. 優先順位・スコープ境界

### P0: 品質・安全の必須基盤（省略不可）

- Source のURL・提供元・対象災害・時点・原本ハッシュ・適用範囲・公開上の制約を保存する。
- 独立 C 検証と人間確認が必要な原本時点／施設同一性／記号の意味をすり抜けない。必要なら機能を UNKNOWN で止める。
- D の正規化・条件評価が決定論的で、B/E は任意の hazard safety 推定を独自追加しない。
- 原本未取得・版不明・対象範囲外・通信障害を、単なる「候補ゼロ」に読み替えない。
- 地図・UIでの失敗／制約の明示と実ブラウザ受入を行う。

### P1: 利用者価値としての必須機能

- 洪水1地域の検証済み入力 → 条件抽出 → 根拠付き比較 → 利用者選択 → 参考経路表示。
- 候補表示と、未確認／不一致／元データ欠損の明確な区別。
- 操作の途中で出典・制約・公式指示への導線を見失わないUI。

### P2: 品質を満たした後の拡張

- 本当に利用可能な公式のリアルタイム配信がある場合に限り、時点つき自動取得を実装・受入する。
- バリアフリー、開設・混雑、経路上の障害、個人条件の評価（出典と最新性を検証できる範囲のみ）。
- 第二の地域・第二の災害種別への小規模 2×2 再検証。既存 [Issue #89](https://github.com/1kz-ma1/HINANEX/issues/89) の地域×災害セルごとの独立ゲートを省略しない。

### 2027-02-09 の対象外（将来像）

- 全国すべて／全災害の網羅・常時リアルタイム保証
- 施設の安全性、開設中、受入可能、推奨優先順位の総合自動断定
- 道路の実際の通行可否や避難経路の安全性の保証
- 自律的な避難指示、救助・避難後生活・復興支援プラットフォームの本番提供

## 6. 実装境界案（共有契約を変える場合は別PR）

設計上のデータフロー（実装済み構造との同一性を保証しない案）:

Official Source / Archived Scenario
→ A: 時点・原本・出典
→ C: 原本／属性／版の独立受入
→ D: Normalization / UNKNOWNを保持した災害条件照合
→ 共通の候補・説明・Evidence（必要なら後方互換の追加契約）
→ B/E: 比較／地図／選択
→ Eまたは外部地図: **選択先への参考経路**

- A: 取得先・公式意味・版・カバレッジを整理。観測されていない事実を作らない。
- C: 原本から出力への追跡、差分、対象災害、誤った結合や時点の混同を独立検証。人間承認はテスト成功と別。
- D: 災害条件の正規化と利用できる条件の評価。Schema と UNKNOWN の意味を保持。
- B: 施設比較・理由・不明・情報時点を読みやすく表示。
- E: 地理的表示、利用者による選択、参考経路UI。空間ハザードの独自安全推定はしない。
- 共有契約・責務をまたぐ設計は事前に合同レビューし、Add → Migrate → Remove を守る。

追加提案のデータ項目候補（未確定）: scenario/source ID、hazard namespace、as-of/retrieved timestamps、source URL/hash、適用範囲、判定の根拠フィールド、UNKNOWN理由、地理情報の精度、経路提供元・更新時点、表示上の制約。現在の RegionExport に全項目があると仮定しない。

## 7. 受入基準（Definition of Done）

### 技術・データ

- 対象地域と洪水情報が正確な公式ソース／固定された原本に結び付き、取得・変換・出力を再現できる。
- 元記号の意味が承認済みの場合だけ条件評価に使われ、承認されない施設は UNKNOWN のまま。
- 誤ソース、誤時点、誤災害、施設ID不一致、欠損座標、範囲外、取得失敗が fail-closed で処理される。
- 検証報告は **PASS / LIMITATION / NOT TESTED** を分け、原本・コミット・テスト実行・人間確認を紐付ける。

### UI・利用体験

- PC とモバイルの実ブラウザで、保存済み対象シナリオを用いて「抽出 → 比較 → 本人選択 → 経路参考表示」を途中で操作不能にならず完走できる。
- 表示理由と元出典の照合ができ、未確認・欠損・対象外・失効時に誤認を生む断定が表示されない。
- 自動取得できない、位置利用を拒否する、ルートサービスが失敗する場合の代替表示がある。
- 参考経路と安全な経路を明確に区別し、災害時の公式指示に従うことを妨げない。
- 外部ルートサービスの利用規約・API制約・利用者位置情報の送信範囲・同意を確認する。

### 発表・公開

- 本番デモの入力ソースと許容される主張を事前に固定し、実装済み／将来構想を区別する。
- 偽の「リアルタイム情報」、証拠のない安全ランク／距離最短＝安全の主張、未承認の施設結合をしない。
- 公開できるのは独立受入した範囲だけ。**展示用 MVP の受入は、実災害下での安全利用許可ではない**。

## 8. 暫定ロードマップ（優先度付き、達成を保証しない）

| 期間 | 主眼 | 節目／終了判断 |
| --- | --- | --- |
| 2026-10-19 ～ 11-15 | P0: 原本・時点・施設同一性・UNKNOWN・再現性のゲート確認 | #268/#264/#265/#266 等の証拠を確認。未承認事項を閉じないまま「基盤完成」と言わない |
| 11-16 ～ 12-13 | P1: 保存済み洪水シナリオと自動条件抽出の接続 | 固定入力で再現可能。誤条件・欠損は UNKNOWN |
| 12-14 ～ 2027-01-10 | P1: 候補比較／選択／参考経路のUI | 参考経路であることを表示。外部連携の同意／失敗処理を含む |
| 01-11 ～ 01-25 | P1: 一連の実ブラウザE2Eと情報の説明可能性 | 入力・データ版・UI・出典の整合、PC/スマホ、異常系を記録 |
| 01-26 ～ 02-09 | 安定化・デモ証拠・発表 | 新規機能追加を原則凍結。失敗時の予備デモと表現監査 |

**進捗判断ルール:** P0 の未承認データを前提に P1 の「安全判定」へ進まない。ライブ災害情報や安全性評価の独立受入が間に合わなければ、固定された検証用入力による参考抽出・比較デモまでを完成成果とし、ライブ連携／安全評価は FUTURE と明示する。一般化の 2×2 テストは放棄せず、基盤の信頼性を損なわない範囲で別マイルストーンとする。

## 9. 要レビューの意思決定と依存関係

1. 最初の洪水対象範囲は「江戸川区の行政資料」か「C-accepted な GSI の地理的カバレッジ」か。両者は異なるソース集合であり、未承認の同一施設結合をしない。
2. 本番デモの災害入力は固定シナリオのみとするか。ライブ連携を採用するなら、提供元、更新周期、時点認証、通信不能時の扱いを先に承認する。
3. 経路表示の提供元、API利用規約、費用、個人位置情報と外部送信の同意、障害時のフォールバックを決める。
4. 候補の並べ方は「絞り込み済みの参考一覧」とし、距離順を安全順・推奨順位と誤認させないか確認する。
5. 現行 #268 のデータ信頼性最優先ゲートと #89 の 2×2 追加検証方針を維持しつつ、3軸の高さをどこで優先するか、Merge Captain と各担当が開発順序を承認する。
