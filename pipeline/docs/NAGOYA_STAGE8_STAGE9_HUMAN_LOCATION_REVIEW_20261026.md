1. **Stage 8**: ABR候補参照点とGSI登録参照点を航空写真に重ねた**人間の目視所見**を収集・記録する。敷地境界・建物・入口の法的または公式な位置確定ではない。

## 3. Stage 9 — 人間主導の独立位置検証

### 3.1 実施条件と役割

- **調査担当（人間）**: ローカルのPRIVATE台帳を権限のある端末で開き、公開の根拠資料を人間が確認し、個別記録に転記する。候補点を平均・補完・自動選択しない。
- **AI**: 検索語・手順の案内、論点の説明、報告文の整形、不備チェック。PRIVATE CSV・生の座標・施設別の比較画像を外部AIサービスへ投入しない。
- **独立レビュアー（人間）**: 同じ担当者の自己確認に依存せず、原資料を自ら開いて判断の再現性・反証可能性を確認する。
- **受入責任者（人間）**: 施設位置について個別に承認／保留／不採用を判断し、根拠と日付・判断者を閉域の記録に残す。AIが代理承認しない。
- **統合担当（Merge Captain）**: 後日のコード・Contract・データ統合を別途審査する。位置受入とmerge許可は異なる。

### 3.2 照合の順序

1. **第1群：重複ABR参照点の2施設**
   - 元住所と施設同一性を再確認し、ABRの`match_level`と`coordinates_level`、応答の版・根拠・共通代表点の可能性をローカルで検査。
   - 同一点になった原因が明らかでなくても、座標を自動採用・訂正しない。GSI登録点と別途公的な位置証拠を比較する。
2. **第2群：その他のABR敷地外目視4施設**
   - ABR候補点が示す対象、GSI点が示す対象、施設配置図・校舎案内・敷地図等との整合を調査。
   - **入口付近に見える**ケースでも、正式な入口と断定しない。
3. **第3群：ABR敷地内目視3施設**
   - 敷地内に見えることを理由に省略しない。施設同一性、建物／敷地／入口のどれを点が代表するかを別資料で検証する。
4. **横断：GSI参照点9件の独立照合**
   - GSIが自治体登録点に由来する可能性や資料の循環参照を考慮し、**GSI一致だけを独立測位証拠としない**。
   - 画像の撮影時期、登録時期、対象の移転・改修・施設名称変更の有無を確認。日付の不明な資料は不明のまま残す。
5. **別担当者の再確認と責任者判定**
   - 施設ごとの資料を別の担当者が再確認し、責任者に位置受入の判断材料を渡す。矛盾・未確認が残れば**HOLD**。

### 3.3 個別施設で確認する証拠（PRIVATE側のみ保存）

- 元の施設IDと元データfingerprintが**同一**であること（元データと照合して再計算、相違は停止）。
- 名称、住所、施設種別（原資料にある限り）、建物・敷地・入口の対象の区別。
- **出典のURL、発行主体、文書名、版、公開／更新／撮影年月**（分からなければ`UNKNOWN`）。
- ABRとGSIの位置参照点に対応する施設同一性、点の意味、ズレ・競合・代表点の有無。
- 住所参照点と施設位置の対応を裏付ける**独立した公的資料**（例: 施設配置図、管理主体の位置図、施設案内の住所・建物識別情報）。同じ出所をコピーした複数地図は独立根拠と数えない。
- 目視記録・公式資料で一致する点、相違する点、解決不能な点とその理由。
- 担当者の所見と確認日、独立レビュアーの所見と確認日、責任者の判断と日時。
- 施設別の詳細、座標、スクリーンショット、候補地図リンク等は**承認されたローカル台帳のみ**で扱う。共有用テキストには必要最小限の公開根拠URLと結果分類のみを書く。

航空写真は補助証拠であり、**敷地境界の確定や入口位置の証明を単独で満たさない**。十分な証拠が得られない場合、架空の座標や「おそらく正しい」という結論を補わない。

### 3.4 受入判定と停止条件

これは**作業記録上の分類案**であり、既存JSON SchemaのstatusやGIS契約へ新しいenumを勝手に追加しない。

| ローカルの検討区分 | 意味 | 次の処理 |
| --- | --- | --- |
| `READY_FOR_INDEPENDENT_REVIEW` | 出典・位置の意味・比較の根拠が揃い、別担当者が検証できる | 人間の独立レビューへ |
| `NEEDS_MORE_EVIDENCE` | 資料・版・位置の意味が不足 | 保留、追加の公的資料を探す |
| `CONFLICT_OR_UNRESOLVED` | 根拠が矛盾／別施設・代表点の疑い／判定不能 | 保留、責任者へ報告 |
| `HUMAN_POSITION_ACCEPTED` | 別担当者の再確認を経て、**権限ある責任者が位置用途・根拠を限定し明示受入** | 非公開承認記録を維持。GIS反映はなお不可 |

以下のいずれかがあれば、位置受入を止める: 施設同一性が曖昧、資料の更新・撮影時期が不明で位置変更の可能性を排除できない、参照点と実施設の意味が混同、資料間で矛盾、出典の独立性を説明できない、責任者・再確認者の判断証跡がない。

**現時点の件数は常に`HUMAN_POSITION_ACCEPTED=0`と報告する。** この文書の追加はその件数を変更しない。

## 6. 重複したABR参照点の原因調査（2026-10-26、暫定）

**調査対象**: Stage 8で報告された「住所が異なる2施設について、ABR候補座標が完全一致し、GSI登録点は異なる」事象。個別名称・座標・PRIVATE行はここには公開しない。

### 6.1 コードから確定できたこと

- `geocode_nagoya_pilot.py`の`classify`は、ABRのGeoJSONの`geometry.coordinates`から経緯度を取り出し、選択済み候補として返す。自分で座標を補間・平均化していない。
- 同`resolve`は、**初期50件の候補内でのみ**完全一致座標を検出し、`shared_reference_coordinate`を付して`NEEDS_REVIEW`にする。
- `create_nagoya_independent_review_queue.py`はStage 4で再照会された候補と初期候補を`reference_origin`付きでPRIVATE台帳に出力する。`reference_origin`は`ORIGINAL_UNVERIFIED_ABR_REFERENCE`／`CHOME_TEXT_EQUAL_ABR_REFERENCE`／`PARCEL_ABR_REFERENCE`等。したがって、**2施設が初期候補だったのか再照会候補だったのかは台帳で区別できる**。
- Stage 4の重複判定は初期候補と再照会候補を横断して行われるが、`screen_exact_reference`は**地番精度（parcel）の要確認分類を座標重複分類より先に評価する**。このため、重複候補であっても重複という理由が分類名から明らかでない場合がある。**重複を位置正しいと承認しているわけではない**。
- Stage 5の`compare_nagoya_gsi_offline.py`はPRIVATEレビュー台帳のABR座標を読み取り、別のGSI座標までの距離を求めている。Stage 6/7も元の位置参照点を維持する。**Stage 5以降の距離計算が二施設のABR参照点を同一化したという証拠はない**。

### 6.2 あり得る原因（未確定）

| 仮説 | 確認する情報 |
| --- | --- |
| ABRが複数住所に同じ地番／住所参照点を返した | 2住所それぞれのABRの`matched_address`、`unmatched_address`、`match_level`、`coordinates_level`とGeoJSON応答点 |
| 代表点の粒度が施設の所在地と一致していない | ABRの地番階層・参照点定義、公的施設位置資料・GSI登録点との比較 |
| 初期候補とStage 4再照会候補の混在 | PRIVATE台帳の`reference_origin`、`resolution.json`のレコード状態 |
| 旧スナップショットと現在のABRデータ版が異なる | `provider_version`、`provider_db_version`、入力fingerprint、2回再照会の正規化結果 |

ABRの`match_level`（住所の一致の粒度）と`coordinates_level`（代表点の粒度）は別である。地番住所が一致していても施設の敷地・建物・入口位置まで一致するわけではない。**同じ座標を返すこと自体だけでABRの実装不具合とは断定しない**。

### 6.3 Mac内だけで実施する最小確認（読み取り専用）

既存のStage 7ブランチと、生成済みPRIVATE台帳を保持している承認済み端末の`pipeline/`で実行する。**コマンドはファイルを書き換えない。施設名はローカルで手入力し、出力に名前・住所・生緯度経度・施設IDを含めない。** 実行は担当者本人が行い、AIがPRIVATEファイルを受け取って代行しない。

~~~sh
# 作業ツリーに未コミット変更がないことを確認してから行う。
git status --short
git fetch origin feature/d-nagoya-stage9-abr-duplicate-diagnostic-20261026
git switch --detach FETCH_HEAD
cd pipeline
python3 diagnose_nagoya_stage9_duplicate_abr.py --pilot-dir data/geocoding_pilot/nagoya50
~~~

**重要な訂正（2026-10-26）**: Stage 7の`gsi_stage7_refined_PRIVATE.csv`にはABR座標とGSI座標がありますが、`reference_origin`と`abr_coordinates_level`は**別の元台帳** `independent_facility_position_review_PRIVATE.csv` にあります。診断にはその元台帳と`independent_review_queue_aggregate.json`が必要です。上記コマンドは[Draft PR #324](https://github.com/1kz-ma1/HINANEX/pull/324)のスクリプトを使用し、両台帳を元施設ID・fingerprint・ABR座標で照合します。Gitのcheckout前に作業中の変更があれば中止して保全すること。PR #324は未統合であり、利用時はコードレビューとCI状態の確認が必要です。

**出力に住所や座標がないことを人間が確認してから、上記の匿名結果だけをチームへ報告する。** エラー時のPRIVATE行やトレースバックは貼らない。`provider_version`やfingerprintの文字列自体もチームの共有ルールに従い必要最小限で報告する。

この確認で明らかになるのは**重複候補の来歴と既存処理での維持状況**であり、ABRの現在の生応答が同じ点を返すか・その点が施設位置として正しいかではない。次に必要なら、**同じABR API版・DB版、ローカル127.0.0.1限定**で2住所を人が再照会し、出力に生座標を出さずに一致/不一致・代表点精度のみ匿名集計する。版が異なる場合は現在と当時の再現を混同しない。

| --- | --- | --- |
| `dataset_fingerprint_and_provider_versions_match` | `true` | Stage 7および元キューと初期解決結果の版整合 |
| `earliest_recorded_origin_group` | `STAGE4_BOTH` | 対象2件とも初期パイロット確定候補ではなくStage 4由来 |
| 両件 `original_pilot_status` | `UNRESOLVED` | 初期パイロットでは正式候補にならなかった |
| 両件 `reference_origin` | `PARCEL_ABR_REFERENCE` | 地番要確認ゲートから取り込まれた参照点 |
| 両件 `coordinate_level` | `machiaza_detail` | **座標の代表点は丁目・小字レベル** |
| 両件 `parcel_review_trigger` | `MATCH_LEVEL_PARCEL_INFERRED_FROM_STAGE4_GATE` | **Stage 4の分類ロジックから** `match_level=parcel` を推定。ABR生応答を直接提示したものではない |
| `same_abr_reference` | `true` | 記録されたABR参照点が2件で完全一致 |
| `gsi_reference_relation` | `DIFFERENT` | GSI登録点は2件で異なる |
| 公開／承認 | false／0件 | Stage 9 HOLD・GIS NO-GO継続 |

**現段階での原因分析**: HINANEXのStage 4はABRが返した参照点を候補として保持し、Stage 5以降はそのABR点を保存してGSIと比較する。住所の照合が地番レベルでも、**位置としては丁目・小字代表点までしか付いていない**ため、別の住所に同一座標が記録されたことを合理的に説明できる。ABRの[公式仕様](https://lp.geocoder.address-br.digital.go.jp/)および[公式事例](https://lp.geocoder.address-br.digital.go.jp/case.html)もこの二つのレベルの違いを明記しており、`parcel` × `machiaza_detail`の組み合わせを例示する。

- **特定済み**: 重複候補の取り込み工程（Stage 4）と参照座標の粒度（`machiaza_detail`）。
- **最も有力な説明**: ABRが別地番に同一の丁目・小字代表点を関連付けている。
- **未確定**: ABR生応答の二件の`match_level`（診断ではStage4判定からの推定）、DBにおける参照点定義・割当の内部理由、自治体が確認する施設位置。
- **誤ってはいけない結論**: 「2施設の敷地が同一地点」「ABRの不具合が確定」「GSIが正しい」「位置承認完了」。

**次の業務判断**: この2件のABR参照座標は施設位置として採用せず、Stage 9で公的な施設配置・所在地証拠による人間の独立確認に進む。必要な場合だけ、同一のABR/DB版を用いる**ローカル**再照会により生応答の照合レベル・代表点レベルを確認する。その際もPRIVATEの生データはアップロードせず、結果は匿名要約のみ記録。

### 6.5 完了の定義

1. 2施設それぞれについて`reference_origin`と初期`resolution`の状態を照合できた。
2. ABR座標重複がどの工程ですでに存在したか、または未解明かを明記した。
3. 元ABRの住所照合レベル・座標参照レベルと、施設の公式位置を混同しない。
4. 根拠がそろわない場合は`ROOT_CAUSE_UNCONFIRMED`としてStage 9のHOLDを維持する。現時点はこれに該当。
5. 位置受入0、全安全フラグfalse、GIS/RegionExport NO-GOを維持する。
