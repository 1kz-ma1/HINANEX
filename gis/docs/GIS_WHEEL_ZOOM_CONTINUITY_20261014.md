# GIS wheel-speed and zoom continuity refinement — 2026-10-14

## User observation and scope
The current mouse wheel/touchpad zoom felt under-responsive even with the 1.5× baseline, and the background map still looked jerky. Update **GIS E presentation only**: responsiveness, tile continuity and independent local settings. Do not change source latitude/longitude, official flood raster meaning, zoom-to-recommendation logic, GSI/D provenance, RegionExport contracts or GIS risk classification.

## Behavior
- New default sensitivity is **3.75×**, 2.5 times the old 1.5× baseline, using Leaflet's wheel pixels per level `round(100 / sensitivity)` = **27px** instead of 67px. Existing `zoomSnap:0` remains continuous, and native pinch behavior is not overridden.
- Slider: 0.5–5.0 in 0.25 steps, initially 3.75; manual user changes apply without changing the map center, zoom or source visibility.
- `wheelDebounceTime:80` (formerly 40ms) groups fast wheel bursts into fewer Leaflet zoom transitions. Keep Leaflet animated zoom enabled and increase the animation threshold from 4 to 5. These are intended responsiveness/smoothness trade-offs, **not a proven frame-rate improvement**.
- Previously the official GSI basemap used `updateWhenZooming:false`, leaving an enlarged tile until zoom end. Now use `true`, throttled via `updateInterval:220` and `keepBuffer:4` so existing and intermediate tiles can be reused rather than swapping all at once. The heavier official flood overlay retains `updateWhenZooming:false` and `keepBuffer:3`; **never hide the hazard layer for animation**. It can still update at the end of a zoom.
- Preferences migrate from `hinanex.gis.gesture.v1` to `v2`: the exact old default of 1.5 maps to 3.75, while explicitly selected nondefault sensitivity and "steps" preferences remain unchanged. Version 2 writes occur on user changes, without location/GPS persistence. Fail closed to default on localStorage errors.
- Retain `?zoomFeel=previous` (100px/level, 0.5 zoom snap, 40ms debounce, deferred basemap updates) and `?zoomFeel=slow` (240px/level, 0.25 snap, 55ms debounce) as test-only A/B comparisons. On the new default branch, selecting settings explicitly overrides those temporary comparison values.

## Verification boundaries
- Required GitHub CI: deterministic E controller tests for default settings, slider, backward compatibility/migration, unchanged flood overlay, throttled base tiles, opt-in diagnostics and no source data changes.
- Existing independent Chromium smoke adds a real wheel zoom on the assembled GIS to catch missing wheel handlers and checks the tile policy. Required CI statically validates its syntax but does **not** execute Chromium or measure FPS.
- Before claiming **visually smooth**, perform interactive staging smoke on desktop mouse/touchpad and mobile Safari, ideally comparing the two query-mode URLs with browser performance tools. Measure frame timing, terrain tile network load and source layer latency; a passing CI or Render Live status alone does not prove perceptual smoothness.

## Follow-up: destination-first zoom (2026-10-14)

Visual feedback identified a flaw in the preceding progressive-refresh strategy: repeatedly rendering **transient zoom levels** can make a fast mouse-wheel gesture feel like a stack of steps even with fractional `zoomSnap:0`.

The updated default is **target-first** without replacing Leaflet's wheel handler:
- Keep pointer-anchored, continuous `zoomSnap:0` and default **3.75×** wheel sensitivity.
- Accumulate nearby wheel events inside Leaflet's native **135 ms wheel debounce** (was 80 ms). Leaflet then resolves a final gesture target in one map zoom call. This adds a small delay before an animation begins, deliberately trading a little latency for fewer repeated transitions.
- **`baseMap.updateWhenZooming:false`** means intermediate background tile levels are *not individually requested during the animation*; after reaching the destination, load the official destination raster tiles. The existing cached imagery may be temporarily scaled while traveling. This is not the same as Google Maps' private renderer, nor does it guarantee that target tiles arrive without network delay.
- The **official flood raster is unchanged**, visible throughout the gesture, and still refreshed on zoom end. No fake hazard overlay or hidden-risk interpretation is introduced.
- Preserve `?zoomFeel=progressive` with the prior 80 ms debounce + intermediate base-tile updates at **the same 3.75× sensitivity** for a controlled apples-to-apples visual comparison. Retain legacy `?zoomFeel=previous` and `?zoomFeel=slow` settings and existing local wheel controls. User settings continue to change only sensitivity/step style; no map/GPS state is saved.
- Existing map/popup/marker zoomend callbacks remain intact. D marker group reuse at integer zoom buckets is unchanged and source geometry is never interpolated.

**Verification scope:** required CI tests cover destination-only tile scheduling, wheel parameter bounds, per-mode comparison options and unchanged official flood raster configuration. The independently authored Playwright smoke checks options and mouse-wheel operation but is not executed by required CI. In-browser frame timing, input responsiveness and actual network tile requests remain to be checked against deployed staging; do not equate CI success with proven perceptual smoothness.

**Rollback:** `?zoomFeel=progressive` restores the previous raster-refresh strategy for comparison without a source/schema change; fully reverting default policy requires a new GIS PR.

## Follow-up: one animation per continuous wheel gesture (2026-10-14)

User feedback after #244: **raster imagery improved**, but the **camera's zoom itself still looked stepped**. The latest GIS E change tackles that second cause without changing source or tile semantics.

For default continuous mouse-wheel handling, a **capture-phase wheel listener** on the Leaflet map container coalesces a burst of input until 135 ms idle, then computes **one final fractional target** using Leaflet's bounded logistic wheel curve. The camera moves once through the public `map.setZoomAround(anchor, targetZoom, {animate:true})` API. It stays centered on the last wheel pointer, clamps to the map's actual dynamic min/max zoom, and caps gesture movement below four zoom levels so built-in Leaflet zoom animation can run. Intermediate wheel events no longer cause their own `setZoomAround` calls. Terrain GSI tiles and the official flood overlay retain #244's destination-first refresh policy; visible hazard data never disappears or changes meaning.

**Compatibility and fallback:** Ctrl/Meta + wheel (including browser/trackpad pinch gestures), Leaflet controls, popup interior scroll, and the user-selected 0.5-step zoom style bypass the custom handler and retain native event flow. A/B switch `?zoomFeel=native` restores the #244 native Leaflet wheel implementation with exactly the same 3.75× default, 135 ms debounce, and destination-only tiles. `?zoomFeel=progressive` still restores intermediary tiles for comparison. Saved gesture preferences, keyboard, +/- controls, touch pinch and map data/contracts do not change.

**Tradeoff:** a 135 ms end-of-burst pause is introduced before the single camera move; very long continuous wheel streams may wait until the user releases the wheel. This prioritizes a single smooth move over immediate frame-by-frame camera response and may not fit every input device. The change is **not Google Maps' proprietary animation engine**.

**Verification:** deterministic controller tests cover repeated wheel events yielding one map animation, pointer anchor, scroll direction, Ctrl+wheel bypass, source-popup scrolling, stepped-setting fallback, clamping at min/max, and old-mode comparisons. An independently authored Playwright smoke records the count of real Leaflet `setZoomAround` calls from multiple wheel events. Required GitHub CI parses that script but does not run Playwright. Desktop trackpad/mouse and Safari physical-device visual and latency acceptance remain essential before claiming measured smoothness; use `?zoomFeel=native` to compare identical raster policies.

## Follow-up: instant old-raster preview, deferred destination tile update (2026-10-14)

The last one-target wheel handler (PR #245) reduced animation restarts but introduced a perceptible **135ms pause before any visual change**. User requested Google-Maps-like feedback where the **existing image is enlarged immediately**, and only the *resolved destination zoom level* triggers different source tiles.

**Default GIS E behavior:** a capture-phase wheel event starts a short GPU-composited CSS `scale` of Leaflet's existing **mapPane**, with the pointer as `transform-origin`. This previews the basemap, official flood raster and presentational map marks together without modifying any official source, fetching intermediate tiles or re-evaluating the geographic map zoom during the gesture. A 65ms CSS transition smooths bursts; the target is computed from the same bounded wheel-delta curve and capped at ±2.75 zoom levels to avoid runaway bitmap scaling. When the input has been quiet for 135ms, remove the temporary style and synchronously call **one** `map.setZoomAround(point,target,{animate:false})`. Native Leaflet then requests destination-level tiles and repositions markers; browser CSS transition and Leaflet camera animation do **not** run twice.

**Cancellation/compatibility:** a competing drag/zoom cancels the pending preview and timer; the synthetic GPU preview is never authoritative map location. Saved sensitivity (3.75× default), user-selected stepped zoom, Ctrl/Meta pinch, controls, popup/detail scrolling, native query comparison `?zoomFeel=native`, and official D/GSI data classification are unchanged. On browsers without individual CSS scale support, fall back to #245's single delayed destination zoom without corrupting the map pane. CSS individual `scale` is used so the existing Leaflet map-pane translation `transform` is not overwritten. Original transform-origin, transition, will-change and scale style values are restored synchronously.

**Tradeoffs:** a brief CSS preview can enlarge already-rendered imagery before the new destination tiles are available, and extreme zoom-out preview may momentarily expose old tile coverage limits. A nonanimated final Leaflet commit can still produce some perceptible settling, depending on tile load speed. This is a narrow UX experiment, not a measured reproduction of Google Maps. Rollback comparison: `?zoomFeel=native` (the #244 native handler with the same tile policy), or revert the GIS-only PR.

**Verification:** deterministic map-controller tests assert CSS preview before zoom/view mutation, anchored scaling, one final Leaflet commit, complete CSS cleanup, cancelled pending gestures, input limit and native step/pinch/popover bypass. Existing independent Chromium smoke asserts synchronous preview, delayed geographic commit, tile scheduling and restoration. Required GitHub `test` executes the controller tests and parses Chromium scripts but **does not run the real page in a browser**; real device/trackpad GPU smoothness, frame-time, and visual tile transition still require staged manual/Playwright acceptance.

 
## Faster destination-image request (2026-10-15)

After confirming that #246's instant CSS image preview matches the requested behavior, user feedback identified a second latency: **the sharp destination image takes too long to appear**.

The default preview now commits the *real* geographic zoom after **70ms idle** instead of 135ms, and the temporary GPU-scale ease is **40ms** instead of 65ms. Both preserve the immediate feedback, geographic point anchoring and destination-only GSI tile loading; no intermediate tile levels are requested. The native/stepped/pinch/scroll paths remain untouched. This removes **65ms of intentional waiting before the final official tiles can begin loading**, not 65ms from the network itself. Public network latency, caching and tile server throughput remain independent bottlenecks and may dominate perceived sharpness.

A controlled comparison at exactly the same 3.75× wheel sensitivity and same tile policy is available with `?zoomFeel=preview135`, restoring both the old 135ms debounce and 65ms CSS ease. Existing `?zoomFeel=native` and other diagnostic modes remain.

For opt-in measurement, `?debugMapPerf=1` now prints `wheel intent-to-commit` latency (including the user's wheel-burst duration and the 70/135ms quiet period) alongside the existing `tile batch` load-time logs. These stay local to browser console and do not transmit coordinates or analytics. Comparing the two measurements can distinguish intentional debounce delay from network/basemap loading. Required CI covers timer constants, legacy A/B behavior, unchanged flood tile configuration and script validity. **Actual frame timing and end-to-end target tile load remain unmeasured until interactive Chromium/real mouse or trackpad QA.**

## P0: raster-only wheel preview and temporary old-tile hold — 2026-10-15

The supplied capture exposed two presentation defects: (1) pin icons and attached popups are enlarged by CSS previewing the entire map pane; (2) existing imagery disappears at zoom commit before destination imagery is ready.

During ordinary wheel input, scale ONLY the existing background GSI tile pane and the independent official flood-reference raster pane, not Leaflet's mapPane or its marker/cluster/popup panes. Retain read-only DOM clones of already-rendered official raster imagery within each original raster pane through the final geographical zoom commit. Never invent a tile URL, assessment, location or hazard status. Clones are presentation-only and may not change map bounds or D marker source coordinates. Correct for Leaflet pane translation at commit and release a clone after its own source layer reports tiles loaded (or if it is no longer loading). Cap old image retention at 1,100ms for the basemap and 650ms for official flood, with a 120ms fade; avoid retaining outdated official imagery indefinitely. Other camera gestures cancel the pending preview, while the zoom initiated by the preview does not cancel its own clone.

Known limitation: a zoom-out can expose geography beyond the previous tile coverage. This P0 change reduces pin scaling and imagery turnover gaps but is NOT verified zero-blank-frame coverage. The old imagery is not authoritative at a newly committed zoom; source classification remains unchanged. Live Chromium/Safari screenshot and temporal frame tests remain required. For direct comparison the earlier whole-map pane preview is preserved under zoomFeel=preview135. P1 will preload ONLY bounded predicted destination basemap tiles to reduce uncovered target areas and network delay, with independent GSI source and no intermediate zoom requests. P2 can improve brief cluster/fade transitions after P0/P1 visual acceptance.

## P1: bounded source-identical destination tile warm-up — 2026-10-15

P0 keeps already-rendered GSI/hazard raster frames while zoom commits. P1 begins preparing only the most likely **destination** GSI background tiles while the user is still CSS-previewing, rather than waiting until the final 70ms pause expires and then starting the same downloads.

After 28ms of quiet wheel input, a browser-only Image cache warm-up projects the already-selected pointer/map position at the current predicted destination zoom. It uses the **same official GSI standard tile root as the Leaflet baseMap**, only the chosen integer tile zoom (round of predicted fractional target), a viewport-bounded tile range, normalized wrapped X, clipped Y, distance-nearest order, and a hard **eight PNG images per gesture**. A gesture freezes the predicted tile zoom after its first warm-up, preventing step-by-step requests for traversed zoom levels if the target continues moving. The tiny image reference cache is dropped after at most 1.5s following commit; drag/pinch cancellation or a new wheel burst resets that budget. A warm-up never changes Leaflet's geographic center, zoom level, marker locations, source evidence, data or safety/risk status. It intentionally does NOT warm official flood hazard raster images, preventing speculative demand and retaining separate GSI provenance.

This is an opt-in code optimization with no persisted location or network telemetry. Browser requests to the existing GSI tile provider reveal coarse tile identifiers just as normal map scrolling does; at most eight additional requests are permitted per wheel gesture, and a changing destination may render some of those unneeded. The provider's cache behavior/network and Chrome/Safari image cache reuse are not guaranteed. The `debugMapPerf=1` console path logs only the count of warm-ups, not geographic coordinates or tile IDs.

CI verifies strict request budget, one predicted tile zoom, canonical GSI URL path, duplicate suppression, cancellation and untouched official flood layer. Real browser cache/network waterfall, visible tile coverage and performance improvements still require explicit integration/visual acceptance. Rollback: revert P1 commit without removing the independent P0 raster-only preview.

## P2: light source-marker appearance transition (2026-10-15)

In the recorded zoom-out/zoom-in, individual D source-backed facility pins and map-only clusters switch at the existing zoom buckets (source records, membership and coordinates are unchanged). A CSS-only 140ms fade-in is now applied to new Leaflet icon DOM nodes only in the D-owned shelter marker pane. No geographic transform, pin-scale animation, moving of real points, assessment-state color, click behavior, or extra tile request is involved. Existing icons remain fully visible; this softens just the visual moment that a newly grouped icon is inserted. The animation is disabled under the operating system's prefers-reduced-motion setting.

This is intentionally much smaller than animating cluster centroids or keeping obsolete marker positions visible for a transition: both would risk misrepresenting source locations. The primary P0/P1 fixes deal with raster/pin transforms and destination tile availability. This P2 cosmetic fade does NOT by itself guarantee continuity of all zoom-bucket cluster membership changes and must be visually accepted separately. Tests are static CSS/scope assertions and required CI; complete browser screenshots/recording replay are not run by CI.
