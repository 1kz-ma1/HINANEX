## 1. なぜ必要か / 現在と未来を混同しない

現在のD RegionExportは江戸川区152、新潟566、名古屋1602レコードの実機確認があるが、3地域の洪水時の施設別Scenario判定はすべて `UNKNOWN`（2026-10-09時点の受入記録）。GSIの参照地点、Dの施設、洪水ラスターは別Source。これらを重ねても避難安全性・開設状況は証明できない。#139/#140の新しい公式原本リプレイも、**江戸川区の照合承認0、洪水適合性判定0**の段階ではあくまで未承認。

「地図上でそれらしい結果が出る」ことと「過去の実災害について検証可能な結果を出す」ことを分ける。目指す成果は:
1. 公式データの来歴・検証状態を説明できる。
2. 事前に確定した時点で使える情報だけから結果を出し、事後実績と独立比較できる。
3. 一致・保留・不一致を隠さず表示し、原因調査につなぐ。
4. **実績との一致が直ちに安全性・汎化性能・災害予測の承認を意味しない**ことを明示する。

## 2. 評価対象の分離（最初に固定する）

| track | 問い | 比較対象（ground truth候補） | 避ける主張 |
| --- | --- | --- | --- |
| **T0: Source-to-output** | 公式原本とHINANEXの取り込み・表示値は整合するか | 独立C監査した同じ元レコード・ハッシュ・行ID | 災害の予測精度が高い |
| **T1: Operational replay** | 当時どの施設がいつ開設されたかを、時点固定データでどこまで再現できるか | 当日の自治体の公式開設・運用記録、同一施設/同一時刻の承認済み対応 | 開設されなかった施設は危険、開設施設は安全 |
| **T2: Hazard/impact replay** | 当時の危険・被害の空間的結果とどこまで整合するか | 時点を明示した確定浸水・観測等の別資料（対象範囲と誤差も監査） | 単一事例だけで将来の安全な避難先を推奨 |

**優先順**: T0 → T1の実行可能性調査 → T1の限定比較 → T2の設計/別ゲート。現在の `flood_shelter_selection` は `UNKNOWN` が正であり、T1/T2の新しい分類を `CANDIDATE/EXCLUDED` に代入しない。T0の成功をT1/T2の成功として数えない。

**時間と比較母集団**: 事前に `event_id`, `region`, `hazard`, `as_of_jst`, `prediction_target`（例: 「当日指定時刻までに開設済みか」ではなく「その後一定時間内に開設されるか」等）, `horizon`, `universe`（施設一覧の版とID）, `truth_cutoff` を固定。比較できる同一施設・同一時刻・同一意味だけをスコア対象とする。開設実績と災害適合性は別ラベル。

## 4. 3パターンの定義と判定規則

比較対象の「予測/推定値」と「独立した実績値」が同じ `track/target/as_of/horizon/identity` で照合可能であることを前提にする。

| 表示 | 機械的条件 | デモで示すもの | 禁止事項 |
| --- | --- | --- | --- |
| **整合 (MATCH)** | 必須Evidence、施設同一性、意味、時点、比較条件が承認済み。出力と実績が事前定義したルールの範囲で一致 | 入力スナップショット → 推定処理 → 実績原本 → 一致根拠 | たまたま数が近い、事後情報で調整した、T0一致を予測成功と称する |
| **判定保留 (ABSTAIN)** | 必須情報欠落、時点不明、未承認join、公式の意味不明、比較対象不足等で主張不能 | 原因コード、欠けているSource/承認、取れる次の対応 | `UNKNOWN`→危険/安全、`NOT_FOUND`→施設不在、未評価→予測不一致への変換 |
| **不一致 (MISMATCH)** | 同じ前提の比較が承認済みで、出力と独立実績が事前定義ルールに反している | 推定と実績の並列表示、差異、原因調査状態 | 裏付けのない原因を断定、誤差を隠す、都合のいい例だけ採用 |
| **比較不可 (NOT_EVALUABLE)** | 実績原本・適切な母集団・同一時点・施設IDが確保できず「正誤」自体を定義できない | 評価対象外件数と理由 | `MISMATCH`や`MATCH`に算入 |

3パターンは**デモで示す主要な結果分類**。統計集計では `NOT_EVALUABLE` / `NOT_RUN` を別記し、3パターンだけに無理やり分類しない。`ABSTAIN` はパイプラインが保守的に動いた事実であって、予測が当たった件数に含めない。`MISMATCH` はモデル誤り、入力データ誤り、運用条件の違い等、**原因未確定**のまま表示してよい。

Cが評価に使う独立の読み取り専用 `ReplayCase/ReplayFinding`（実装前の概念I/F）。D `RegionExport v0.9`、既存 `ScenarioResult`、B/E表示側は一切変更しない。

- `explanation`, `next_investigation`, `limitations`

判定を出す責務は C の独立検証器、データ取得・正規化は A/D、画面のプレゼンは B/E。**表示側で独自に再分類しない**。契約実装が必要になった時点で別の shared Contract RFC を作り、A/B/C/D/Eでレビューする。

### 時点固定とデータリーク防止

1. Aが各データ原本の「当時公表済みか」を発行時刻単位で確認し、INPUTを `release_time <= as_of_jst` に限定。取得日時だけでは代用しない。
2. 当時の施設マスターが欠けていれば推測join禁止。2026年データを入力に入れない。TRUTHは別アーカイブ、別キー、別担当で保管。
3. Dは固定入力＋固定コードSHAで決定論的に実行。ネットワーク再取得に依存しないリプレイ経路を新設する場合はD担当PR。
4. Cはハッシュ、欠損、再実行一致、出典の解釈、未来情報混入、施設ID一致、境界時刻、誤った比較対象を独立監査。
5. 事前に評価ケース集合と一致条件を確定し、結果を見てケースを恣意的に入替えない。開発中に見た事例は検証セットと分け、最終発表では未使用の別事例で再評価。

## 6. 精度の表現と誤読防止

- `N_total`: 事前登録した評価対象の全レコード/施設・時点ペア数。
- `N_eligible`: 同一母集団・同一時点の独立実績があり、評価可能とCが承認した数。
- `N_match`, `N_mismatch`, `N_abstain` は **N_eligible内で互いに排他的**。それ以外は `N_not_evaluable` と分ける。
- `coverage = (N_match + N_mismatch) / N_eligible`（判定可能率）、`agreement = N_match / (N_match+N_mismatch)`（判定対象内一致率）。分母0では`N/A`で表示。
- `abstention = N_abstain / N_eligible`、`non_evaluable = N_not_evaluable / N_total` を**併記**し、一致率だけ高く見せない。
- 必要に応じて、同じラベルと十分な母集団が揃った後に誤検知/見逃し、precision/recall、施設種別や地域ごとの内訳を追加。
- 不一致原因（Source/時点/ID/意味/パイプライン/運用差/不明）は **分析ラベル**。調査前に原因が確定したと見せない。事前登録した許容誤差を後から広げない。
- 紹介する3枚の事例カードは見せ方であり、全件スコアを併記してチェリーピックを防止する。

## 7. 中間発表の実機デモ設計（提案; B/E未着手）

目指すUIは `検証ケース選択 → 同一画面で入力時点/出力/実績/差異/根拠を表示`。**「3パターン表示」ボタンはC承認済み実データの対応ケースが存在する場合だけ有効**にする。そうでない場合は「未検証」「説明用サンプル」の明確なバナー付き閲覧モードに限り、実機実証とは呼ばない。任意クリックで成果ラベルだけを変える演出は禁止。

~~~text
[過去災害の検証] 2019台風19号 / 江戸川区 / 時点:（検証済み日時）
[Track: T0取り込み検証 or T1開設状況 or T2災害結果] [評価範囲と件数]
[整合ケース] [判定保留ケース] [不一致ケース] ※C検証済みケースのみ選択可
┌─ 当時利用できた入力 ─┬─ HINANEXの出力 ─┬─ 事後の公式実績 ─┐
│ 出典・公表時刻・SHA │ 判定・根拠       │ 出典・時刻・SHA    │
└───────────────────┴─────────────────┴────────────────────┘
[照合結果・理由] [欠損/不一致の原因調査] [原本へ] [限界/評価数]
~~~

画面上で「判定保留」が見せるのは現行Dの `UNKNOWN`（正の振る舞い）。`MISMATCH` は本当にC承認済みの独立実績との比較がある場合だけ使用。画面上の成功/失敗を緑赤の危険ランクに見せず、**検証結果の状態**としてのみ表示する。

**推奨90秒の差替え候補**（既存 `gis/docs/DEMO_ACCEPTANCE_20261022.md` の90秒台本は、Eレビューまでは変更しない）:
- 0:00–0:15 シナリオ・基準時点・T0/T1/T2区分を示す。
- 0:15–0:35 整合ケースの「公式原本→入力→HINANEX出力→独立した実績」を展開。
- 0:35–0:55 判定保留ケースで欠損/時点/同一性の不足を開く。
- 0:55–1:15 不一致ケースで実績との差・原因調査中を開く。承認済みケースがなければ**「未検証のため実証なし」**を示す。
- 1:15–1:30 集計母数・判定保留率・評価対象外と今後の検証を説明する。

事前読み込み・操作1〜2クリック・外部ネットワークへの依存抑制・原本閲覧URL・C承認タグ・オフライン録画を受入条件とする。手元UI/録画も同一SHAの再現ケースを用いる。ライブが失敗したら**検証済み映像**に切替え、偽データを「当日の再現」とは言わない。

## 8. 受入条件と停止条件

**設計のみの完了条件**
- [x] T0/T1/T2、MATCH/ABSTAIN/MISMATCH/NOT_EVALUABLEの意味と境界を文書化
- [x] as-of入力と事後実績の分離、再現性、監査項目を設計
- [x] 3パターンデモと虚偽表示を防ぐfallbackを設計
- [ ] A/B/C/D/Eレビューにより正式な対象track/事例/時点/比較母集団を確定
- [ ] 既存 #89 の基礎DoDを証拠付きで受入
- [ ] T1/T2用の公式歴史資料の機械読取・再配布可否をA/Cが独立確認
- [ ] 過去の正答と入力の隔離が自動検証される
- [ ] 少なくとも各ラベルの実データがC承認される（不足ならそのラベルは実証として表示しない）
- [ ] 完全な件数・不一致原因の未確定表示・原本追跡・ブラウザ実機・録画fallbackを検証
- [ ] Merge Captainが独立PRの安全性/統合順を承認

**失敗時の振る舞い（Fail Closed）**: 文献の記載時刻が曖昧、当時版未入手、施設同一性未承認、T1とT2の混同、現行データ混入、生成値不一致、ハッシュ不一致、C監査未了、外部地図タイル欠損等があれば、`ABSTAIN`/`NOT_EVALUABLE`/`NOT_RUN`とし、見かけ上の合格値を生成しない。実災害時の避難判断、リアルタイム安全/開設/経路推薦には使用しない。

## 10. レビュー時に確定する判断（担当を跨ぐ未決事項）

1. **最初の評価track**: 既存基礎のT0から始め、T1/T2の実証は公式資料と比較母集団が揃ってから承認する。
2. **施設・時点の比較単位**: 機械可読な開設実績が施設単位で存在しない場合、集計総数は施設別予測の正答ラベルとして扱わない。
3. **共有I/F**: 既存D `RegionExport`に無断で replay fields を追加しない。C提案の独立レポートを先行し、必要なら別RFC。
4. **UIの所有**: B＝説明・比較パネル、E＝地図への紐付け。どちらが初回導線を持つか、担当レビュー後に決定する。
5. **発表日までの最低ライン**: 現行Eの約90秒デモ、公式出典の閲覧、1件以上のSOURCE→OUTPUT監査、実在する判定保留の説明。実データの予測成功・失敗が揃わなければ、検証計画と課題として率直に報告する。

## 11. 仕様変更・実装時の判断規則

この仕様を超える機能（経路推奨、避難安全の断定、モデル学習、予測エンジン、多地域一般化、時刻未固定の比較）の追加は**自動採用しない**。担当がEvidence/Contract/責務・デモ範囲・テストと別PRを提示し、ユーザー/チームが承認したものから段階的に着手する。元の設計意図を保ったまま、実際の検証で明らかになった問題に応じて変更履歴を記録する。
